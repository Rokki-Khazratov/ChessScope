# Scope and requirements

Status: baseline requirements; implementation not authorized by this document

## Release framing

The first product release is **database plus player analytics**. It is not the full end-state platform and does not require natural-language investigation to be considered useful.

The architecture must nevertheless preserve an evidence contract so an AI layer can be added without rebuilding every service.

## MVP capabilities

### Data intake

- import PGN files with games, tags, comments, variations, NAGs, and clock annotations where present;
- import a user's Lichess games with explicit authorization;
- import a user's public Chess.com game archives within API rules;
- report malformed, duplicate, ambiguous, and partially imported records;
- preserve raw source material and import provenance.

### Database and exploration

- search games by player, opponent, color, date, result, rating, time control, event, opening, and exact position;
- resolve player aliases without silently merging uncertain identities;
- open a game at the matching position;
- show a continuation tree with counts, W/D/L, ratings, dates, and representative games;
- save searches and stable links to result sets.

### Game workspace

- board and move navigation;
- main line and nested variations;
- text comments, NAGs, graphical annotations, and diagrams;
- chapter grouping for research and preparation;
- import/export of supported PGN semantics with explicit loss reporting.

### Player analytics

- repertoire distribution and normalized entropy;
- opening performance with opponent-strength adjustment;
- time-window comparison and visible sample sizes;
- cohort and corpus selection;
- drill-down from metric to contributing games.

### Engine analysis

- local and cloud execution through one job model;
- explicit quick, standard, deep, and research budgets;
- MultiPV, centipawn/WDL, principal variations, engine/version, and hardware/job provenance;
- cancellation, timeouts, deduplication, and cached reuse.

### Evidence

- every aggregate returns filters, sample size, corpus version, metric version, and source IDs;
- every engine claim returns position, engine identity, options, and budget;
- exports preserve evidence references or clearly declare when they cannot.

## Later capabilities

- natural-language analytical investigations;
- novelty and preparation-surprise models;
- conversion and recovery metrics based on calibrated engine labels;
- similar pawn-structure and piece-configuration search;
- repertoire building and training;
- coach/team workspaces and collaboration;
- licensed professional OTB datasets;
- desktop/local companion and offline workflows;
- human-move models and rating-conditioned practical difficulty.

## Explicit exclusions

- online matchmaking or game server;
- tournament pairing and administration;
- generic social feed, news, streaming, or marketplace;
- unrestricted production SQL generated by an LLM;
- bulk mirroring of third-party platforms without clear rights;
- public redistribution of a user's licensed commercial database;
- a native mobile application before validated mobile workflows exist.

## Functional acceptance examples

1. Given a legal FEN and filters, exact-position search returns all matching visible games and no games that fail canonical position verification.
2. Given two aliases for one known player, search resolves them to one canonical entity while retaining source spellings.
3. Given five games, analytics labels conclusions as low-confidence rather than presenting stable traits.
4. Given an engine result, another worker can reproduce the job from stored configuration.
5. Given a metric card, a user can open the contributing game set without reconstructing the query.

## Cross-cutting requirements

- accessibility target: WCAG 2.2 AA for the web application;
- keyboard-first operation for board, notation, search, and command palette;
- locale-safe dates, names, and notation;
- tenant and private-corpus isolation;
- idempotent imports and jobs;
- observability of freshness, completeness, latency, and compute cost;
- deletion and export paths for user-controlled data;
- graceful behavior when engines, external APIs, or AI providers are unavailable.

## Requirement conflicts to resolve by research

- web-first simplicity versus local professional workflows;
- corpus breadth versus licensing and curation quality;
- fast exact search versus flexible analytical dimensions;
- deep engine analysis versus predictable cost;
- collaboration convenience versus preparation secrecy;
- beginner clarity versus professional information density.
